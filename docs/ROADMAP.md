**New precedent:** the Supabase CLI **does** follow imports out of `supabase/functions/` into
`shared/lib/`. No re-export shim needed. Edge functions can share code with the Next app rather than
duplicating it — the four deliberately separate vertical modules stay separate for a *design* reason,
not because the bundler forced them apart.

**S290 closed the top of the chain.** Every genericization from S279–S289 operated on content `provision-tenant` had already written — and that function recorded **no vertical at all** while seeding pest content for every tenant regardless of trade. It now captures the trade from a selector in both wizards, validates it before the write (a bad value 400s rather than hitting the CHECK constraint inside an upsert that logs and continues), and seeds `page_content`, `settings.seo`, per-page meta and service-area meta from it. An unrecorded vertical seeds five platform pages, **zero** service pages, and names no trade anywhere.

**DEPLOYED, not just merged** — `provision-tenant` **v99, ACTIVE, `verify_jwt:false`**, all five files confirmed in the live source. Nothing from this arc is sitting inert.

The public shells are **no longer pest-specific**. Copy resolves `vertical preset (code) → tenant DB override → render`, so one set of shells serves any trade.

- **`shared/lib/verticals.ts` is the bottom layer** — `VERTICALS` (pest, irrigation, lawn, pool, hvac, roof, trailer), `Vertical`, `isVertical`, `resolveVertical`. It lives in `shared/lib` and not `src/shells` because **`shared/` must never import `src/`**; the reverse direction would close a cycle. A test scans `shared/lib` for any `src/` import and fails if one appears.
- `src/shells/_shared/serviceEntry.ts` re-exports the registry, so its consumers were unchanged.
- `src/shells/_shared/verticalCopy.ts` — 15 copy slots, `getVerticalCopy` is Partial + throw.
- `shared/lib/seoSchema.ts` — frozen vocabularies + `getSchemaVocabulary`, same shape. JSON-LD `knowsAbout` now resolves per vertical (pest tenants byte-identical; pls emits irrigation terms).
- **Adding a vertical:** one line in `VERTICALS`, then presets in `verticalCopy.ts` and `seoSchema.ts`. TypeScript flags every consumer that must change.

**Two rules govern preset content.** (a) A preset holds only what is true of the whole TRADE — tenant facts (warranty terms, licence numbers, region, ratings, scheduling promises) belong in the DB. (b) Never fabricate: the about stat block's invented figures are gone, `settings.about` drives it, and no stats configured renders **no block** rather than a fallback tile.

**Fail-loud has a cost.** `getVerticalCopy` and `getSchemaVocabulary` both throw from `layout.tsx`, so a tenant set to a copyless vertical 500s the entire site — triggerable by a JSONB edit with no deploy. Chosen deliberately over serving pest copy to a pool company. **The CHECK constraint IS now applied** (S281, `supabase/migrations/20260823210305_s281_business_info_vertical_check.sql`): `settings.business_info.vertical` must be `'pest'`, `'irrigation'`, or NULL, so the fatal JSONB edit now fails at the database with 23514 instead of taking a site down. Rollback script sits alongside it, deliberately untimestamped so the CLI cannot apply it.

**The vertical is now BACKFILLED and load-bearing** (S281 + Claude.ai, verified by count query): `'pest'` on the seven pest tenants, `'irrigation'` on `pls`, and deliberately **NULL on vita-glow** — a medical-aesthetics business that is not pest. That NULL is why the neutral fallback has a real consumer rather than being defensive decoration. No rendered content changed; no ISR purge was needed.

**Three layers now resolve on `vertical`, and they are DELIBERATELY SEPARATE modules:**

| layer | module | reader |
|---|---|---|
| public site | `src/shells/_shared/verticalCopy.ts` | a prospect on the marketing site |
| generated copy | `supabase/functions/_shared/verticalCopy.ts` (S283) | an LLM writing a report |
| admin labels | `src/lib/adminVerticalPreset.ts` (S285) | the owner in their dashboard |

They do not import one another. A wrong noun in the generated-copy module produces a fabricated sentence in a customer-facing report; a wrong label in the admin module produces a confusing dropdown. Different blast radius, different change cadence — merging them would couple a prompt rewrite to a UI relabel.

**Keyed on `vertical`, never on `industry`.** `industry` is free text from an onboarding input: `pls`'s stored value is a 154-character service description, vita-glow's is "Medical Aesthetics". Neither would ever match a lookup key, which is why `ComposerTemplates`' `INDUSTRY_TEMPLATES` silently fell through to `generic` for both — the right answer by the wrong mechanism.

### Learnings — read before writing a migration

- **`CREATE FUNCTION` inherits default privileges; `REVOKE ... FROM PUBLIC` does not remove a role grant. Always re-read `proacl` after creating a function — never assume the REVOKE covered it.** Learned the expensive way in S309: `list_tenant_members(uuid)` was created with an explicit `REVOKE ALL ... FROM PUBLIC` immediately after it, and still landed with `anon=X/postgres`, because Supabase's `ALTER DEFAULT PRIVILEGES` on schema `public` grants EXECUTE to `anon` and `PUBLIC` is a different grantee from `anon`. The migration's own comment asserted the opposite and was wrong for a full deploy cycle. `CREATE OR REPLACE` behaves differently again — it preserves the existing ACL rather than re-applying defaults — so two functions in the SAME migration block came out with different grants. **The check is one query and it is not optional:**

  ```sql
  SELECT proname, pg_get_function_identity_arguments(oid) AS args,
         coalesce(array_to_string(proacl,' | '),'(default: PUBLIC EXECUTE)') AS acl
  FROM pg_proc WHERE proname = '<fn>';
  ```

  And the counterpart rule, from S308's B2: **revoking `anon` is only safe when no RLS policy references the function.** An RLS predicate evaluates as the querying role, so a role without EXECUTE cannot evaluate a policy that calls the helper and every such policy fails closed. `is_operator()` and `is_tenant_member(uuid)` grant `anon` deliberately for exactly that reason. Check `pg_policies` before copying a REVOKE.
